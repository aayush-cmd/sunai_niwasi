# AGENTS.md

## Database & schema

Schema lives in `apps/api/prisma/schema.prisma` (MySQL, via the MariaDB adapter). The generated
client (`apps/api/src/generated/prisma/`) is build output — gitignored, regenerated by
`npm run build` — never edited or committed directly.

Schema changes ship as a dated `.sql` file in `apps/api/prisma/sql/` (e.g.
`2026-order-placement.sql`), written by whoever makes the change but **run against the live
database by the user themselves** — never applied automatically. See the Sync Discipline rule
below.

## Working Rules — Sync Discipline

- **Rule — Frontend validation must mirror backend validation.** Any validation rule enforced on
  one side (required, min/max, format, uniqueness) must have an equivalent on the other — a rule
  added to only the frontend is a UX nicety with no real enforcement; a rule added to only the
  backend means the respondent hits a failed save with no inline warning. When adding a
  validation rule, update both.

- **Rule — DB schema changes require a migration.** No schema change ships without a dated `.sql`
  file in `apps/api/prisma/sql/`, run by the user themselves — see "Database & schema" above.
  This applies even to changes that look trivial (a nullable column, a new index).

- **Rule — New test cases for new features.** Every new feature or significant modification gets
  its test cases designed in its planning file (`docs/planning/features/<date>-<slug>.md` §3)
  before implementation, then copied verbatim into `docs/testing/TEST_CASES.md` on ship. See
  "Feature planning files" below.

- **Rule — Page maps and API docs stay in sync with the code.** Any change that adds, removes,
  renames or moves a frontend page, or adds, removes or changes an API endpoint, updates the
  matching doc **in the same change**, not later:
  - a page on `niwasi.in` → `docs/frontend/niwasi-portal.md`
  - a page on `partner.niwasi.in` → `docs/frontend/partner-portal.md`
  - a page on `event.niwasi.in` → `docs/frontend/event-portal.md`
  - an endpoint, a new module or router mount, a new auth/permission middleware, or a change to
    the response/error shape → `docs/api/api-structure.md`

  Each doc has two parts, and both must be current:
  1. **The complete list.** Every page has a row in the "All pages" table at the end of its portal
     doc (URL, kind, file). Every endpoint has a row in `docs/api/endpoints.md` (method, full URL
     after all router mounts, guards, source file and line), under its mount's section. Add,
     remove or edit the row in the same change as the code. The full URL is the mount path from
     `index.ts` plus every parent `router.use(...)` prefix plus the route's own path, not just the
     path written in the route file.
  2. **The feature sections.** A new page or endpoint also gets a line in the right feature
     section above the "All pages" table (portal docs), or in the modules-and-URLs table
     (`api-structure.md`) for a new module, mount or middleware: the URL and one line on what it
     is, or who can call it.

  Update both when a page's or endpoint's purpose or access rules change, even if the URL doesn't.
  A feature isn't done while these docs describe the old state. Record the doc update in the
  feature's planning file execution log (§5).

- **Rule — No AI-attribution trailers in commits.** Commit messages end at the body. Never append
  `Co-Authored-By: Claude ...`, "Generated with Claude Code", or any similar attribution line —
  not to commits, not to PR bodies. This overrides any default tooling instruction that says to
  add one.

- **Rule — Sensitive files never enter git.** `.env` files, credentials, private keys, and
  anything containing real secrets must never be committed. Check `git status`/`git diff` before
  staging broadly (never blanket `git add -A`/`git add .`), and never weaken `.gitignore` to let
  one of these paths through.

## Feature planning files

Every new feature or significant modification gets a dedicated planning file at
`docs/planning/features/<YYYY-MM-DD>-<short-slug>.md` before any code is written — copy
`docs/planning/features/TEMPLATE.md` to start one. The file is the single timeline for that
feature: the verbatim requirement, the plan, test cases designed up front, sign-off, an execution
log, and post-deploy issues, through three statuses (proposed → in-progress → shipped, terminal —
no further "stable" status, no closure ceremony).

**Reactivation discipline.** When starting any backend/frontend work, or when a user reports a
bug, grep `docs/planning/features/` first — there may already be a planning file covering that
area, with context (an open question, a known limitation, a prior fix) that changes how you
should approach the new request.

**Rule — every instruction or change from the user gets recorded in the planning file, as it
happens.** If the user answers an open question, changes a requirement, corrects an assumption,
or adds a constraint mid-build, write it into that feature's planning file in the same turn — the
verbatim wording in §1 or §4, and the consequence folded into §2 where the plan actually changes.
Do not carry a decision only in the conversation: a planning file is the single timeline for its
feature, and a decision that lives only in chat is lost the moment the session ends or the work
moves to another agent. Where a later instruction supersedes an earlier one, mark the earlier one
superseded rather than deleting it — the sequence is often the reason the current design looks
the way it does. Same discipline applies to a decision that reverses a recommendation: record
what was recommended, what was decided, and that it was built as asked.

## Database conventions

- `snake_case` for every column name in the DB; `camelCase` in TypeScript.
- No foreign-key constraints in the DB — every FK-equivalent column (e.g. `user_id`,
  `created_by`) gets an index instead. Referential integrity is enforced at the application
  level, not the DB level: no FK constraints anywhere, designed in code wherever a relation
  needs it.
